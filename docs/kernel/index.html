@nanoagent/kernel

Not a harness. Kernel advances one state machine through phases and commits revisioned AgentRunState. Caller owns sessions, prompts, tools, providers, storage, UI, and product policy. Every core lifecycle boundary has a hook checkpoint and a streamed event.

Why

I kept wanting the same low-level agent loop with different production choices around it. Existing SDKs and harnesses helped when I accepted their runtime shape, storage model, protocol, tool registry, permission system, compaction strategy, retries, and product policy. They got in the way when I needed control over the execution state itself.

Most agent harnesses feel like frontend frameworks from the early 2010s: Backbone.js, Angular.js, and the era where framework owned routing, state, templates, lifecycle, plugins, and application shape. I wanted the agent-loop equivalent of crisp React: small core, explicit data flow, caller-owned architecture, and enough lifecycle hooks to build real products without inheriting someone else's app.

I wanted uneven state: run snapshots in Postgres, bulky transcript artifacts and traces in S3, and message history loaded from remote storage fresh on each turn. Existing SDKs usually made session persistence part of their product runtime instead of giving me a small durable state machine I could persist however I wanted.

I wanted to experiment with compaction: summarize old turns into a system note, keep tool results but drop intermediate reasoning, build retrieval chunks from transcript history, or compact only when remote message storage crosses a token budget. Existing abstractions tended to bake compaction into the harness, or hide the exact boundary where future model input is assembled.

I wanted an inbox so incoming user messages could queue up and steer the next turn. I wanted some agents to rebuild model messages from remote storage every turn, not from an internal transcript chosen by the SDK. That means the loop needs a clean preparation point before every model call.

I wanted tool policy at two levels: inspect the entire set of tool calls for a turn before any call runs, then inspect each individual call with its arguments. Existing permission systems were often product-specific switches around a tool registry, not checkpoints in the execution state.

I wanted provider-agnostic model routing and live streaming of tool requests while the model was still producing them. I wanted to swap OpenAI for Anthropic, route tenants through signed gateways, and resume from the last committed phase without adopting someone else's CLI, server, store, or session object.

Kernel extracts the part that keeps getting rewritten: advance turns, call the model, expose streamed parts, run tools, commit ordered state, pause, resume, fail, and complete. Every boundary exposes both control surface and event surface: hooks decide what happens next, events tell the outside world what just committed. Everything else stays in caller code because production agents are differentiated by those decisions.

Not a harness

The kernel is one function — runAgent. No runtime, no scheduler, no storage adapter, no CLI, no router. It plugs into whatever surrounding system you've already built.

Runtime. Wrap runAgent in an HTTP handler that streams events to SSE or WebSocket, a queue consumer that processes resumable jobs, a CLI that writes events to stdout, a durable function (Cloudflare Durable Objects, Temporal, Inngest), or a unit test iterating fully in-memory. Same kernel; the wrapper is whatever surface you need. Kernel doesn't own the process.

State. saveState is a plain async function, so state lands wherever you write it — Postgres, SQLite, Redis, blob storage (S3, R2, GCS), local filesystem, remote filesystem (NFS, FUSE, SFTP), Cloudflare Durable Objects, or an in-memory map for tests. No adapter SDK to learn, no storage interface to implement; just write the snapshot the way you'd persist any JSON.

Everything else. Providers, tools, and middleware are caller-supplied too — kernel doesn't import a model SDK, execute a tool, or wrap an I/O call unless you pass it in. The same kernel runs behind a real-time chat UI, an overnight batch job, and a debug CLI; only the wrapper changes per surface.

API

runAgent is an async generator. Configure it with hooks (only onTurnPrepared is required), tools, middleware, and a saveState persister. Each core lifecycle phase has a matching hook and streamed event; drive the loop by iterating those events. 

import { runAgent } from '@nanoagent/kernel'

for await (const event of runAgent({
  state: { context: { userId } },              // caller-owned context shape
  maxTurns: 10,

  hooks: {
    onTurnPrepared: ({ context, state }) => ({ // required: build model input
      model: 'openai/gpt-5.5',                  // <provider>/<model>
      messages: assembleMessages(context, state),
    }),
    onToolCallStarted: ({ toolCall }) =>         // optional: gate, skip, rewrite
      gateApproval(toolCall),
    // one hook per phase — see Run Lifecycle for the full set
  },

  tools: { searchDocs, runQuery },             // Vercel AI SDK tool set

  middleware: {
    callModel: [withCache, withTracing],       // wrap streamText
    callTool:  [withSandbox],                  // wrap tool execution
  },

  saveState: async ({ state, events }) => {    // durability boundary
    await store.commit({ state, events })
  },
})) {
  publish(event)                               // forward to UI, queue, log
}
Run Lifecycle

runAgent is one async generator. It advances a run through ordered phases, commits AgentRunState before each durable event, yields those events to the caller, and also yields live stream_part events while the model is producing output. Hooks are checkpoints inside this flow; the public shape is the event stream you iterate.

Events

runAgent is an async generator. It yields durable phase events plus live model stream_part events. The phase events are the same objects passed to saveState; stream parts are live only.

One phase event is yielded per phase transition. The type field matches the phase name — run_started, turn_prepared, model_completed, tool_call_completed, turn_completed, run_completed, and the rest. Each carries runId, revision, createdAt, and a snapshot of the current turn; some add duration and phase-specific payload (model args/result, tool input/output, completion source).

Three additional lifecycle events flow through the same channel: pause when a hook pauses the run (carries the phase it paused at), model_restarted on resume from model_started instead of re-emitting it, and run_failed with a serialized error. saveState.events contains this same AgentPhaseEvent type, scoped to the current state commit.

During model_started, every part the model produces yields as a stream_part event — text deltas, tool-call deltas, reasoning, finish reasons, warnings. The payload is the raw Vercel AI SDK TextStreamPart on .part, plus runId, turnId, and turn number for routing; onStreamUpdate observes the same parts inside the kernel. These are not AgentPhaseEvent values and never appear in saveState.events. Kernel commits the final AgentModelResult on model_completed.

Control from any hook

Control is caller-owned. Every hook is a checkpoint that can let the run proceed, pause it durably, finish it, or force another turn. Hooks return { context, value, control }, and the kernel awaits each one before committing the next phase. Approval queues, budget gates, policy checks, model calls, and external waits live in hook code without a separate scheduler.

pause works from any hook at any moment in the run. It commits a paused snapshot at the exact phase boundary, emits a pause event, and stops before more work starts. Resume by passing the saved state back into runAgent. Use it for human approval before a tool runs, rate limits, budget holds, worker handoff, webhooks, CI results, and user decisions.

finish queues a caller-sourced run completion at the next checkpoint. Product code decides when the goal is met: structured output validated, content approved, cost ceiling reached, or downstream system accepted the result.

continue forces another turn after turn_completed even when no tool calls ran. Use it for critique passes, judge turns, validators, draft-revise loops, and multi-stage flows where product workflow decides completion.

Terminal states

completed — sources: model_done (no tool calls last turn), max_turns, or caller (hook returned finish).

failed — onRunFailed fires, the error is serialized into state with the failed phase, and re-thrown to the caller's iterator. Passing the snapshot back to runAgent resumes from that phase.

paused — resumable from the saved phase; onModelRestarted fires when resuming from model_started.

saveState

The durability boundary. Kernel calls saveState({ state, events }) before every phase event yields — same call for live, paused, and failed snapshots. Awaited; if it throws, the run fails. Optional — omit it and the kernel still runs, just nothing persists.

Invocation. Fires on every state commit, before the matching events reach the iterator — so anything the caller observes is already durable. state is a fresh deep-clone of the new snapshot; events is the commit-local list of phase events about to emit. It is the delta from the previous committed revision to this revision, not full event history.

Atomic unit. State and events share the same revision. Persist them together — one transaction or batch — and readers get exactly the state that produced the events. Use state.revision for optimistic concurrency: reject writes whose revision isn't greater than the stored one.

What to store. Latest state keyed by runId is enough to resume. Append-only events keyed by (runId, revision) give you audit log, replay, and projections (UI feeds, metrics streams). Insert only events from current saveState call; never reinsert prior revisions. Either or both. 

const saveState = async ({ state, events }) => {
  await db.transaction(async (tx) => {
    // commit-local phase events for state.revision only
    await tx.insertEvents(events.map((e) => ({
      runId:    state.runId,
      revision: state.revision,
      payload:  e,
    })))

    // upsert latest state — reject stale writes
    await tx.upsertState(state, {
      where: { revision: { lt: state.revision } },
    })
  })
}
Resume & recover

With state persisted, both pause and failure become resumable checkpoints. Load the snapshot and pass it back to runAgent.

Resume from pause. Pass a status: paused snapshot back as state on the next runAgent call. Kernel flips status to running at the saved phase and continues. onModelRestarted fires when re-entering model_started.

Recover from failure. Failed runs commit status: failed with a serialized error and the failed phase, then re-throw to the iterator. Pass the snapshot back to runAgent to retry from the saved phase after inspection, operator action, or a later user message.

Provider failure. If streamText fails because provider returns 500, run has already committed model_started. Kernel saves status: failed with phase: model_started. When provider recovers, pass same snapshot back; kernel emits model_restarted and reruns the model call with the saved turn args.

Recover from process exit. If the process exits, load the latest committed snapshot and pass it back as state. A running snapshot continues from its phase; model_started restarts the model call. In-flight tool calls stay guarded because external side effects may already have started. 

async function runOrResume(runId, context) {
  const saved = await store.load(runId)

  for await (const event of runAgent({
    state: saved ?? { runId, context },         // fresh or resumed
    hooks: { onTurnPrepared },
    maxTurns: 20,
    saveState: async ({ state, events }) => {
      await store.commit({ state, events })   // fires on every phase
    },
  })) {
    publish(event)                              // UI, logs, queues
  }
}

// On pause:   store has status: paused — call runOrResume(runId) again to continue.
// On failure: store has status: failed + phase + serialized error — inspect, then
//             call runOrResume(runId) again to retry from the saved phase.
// On 500:     failed phase is model_started; retry emits model_restarted and calls the model again.
// On exit:    store has the last committed running snapshot — restart worker and call runOrResume(runId).
Providers

onTurnPrepared returns the model as a string like openai/gpt-5.5 or anthropic/claude-opus-4-7. Kernel splits on the first /, looks up the provider in its registry, and calls the provider function with the model name to get a Vercel AI SDK model that streamText drives. Provider keys are case-insensitive and trimmed.

Bundled. The major Vercel AI SDK providers are registered by default — no setup needed beyond the relevant API key in env: openai, anthropic, google (alias gemini), vertex (alias google-vertex), azure, bedrock (alias amazon-bedrock), xai (alias grok), mistral, cohere, deepseek, groq, perplexity, cerebras, fireworks, together (alias togetherai), deepinfra, baseten, vercel.

Custom & override. Pass modelProviders to runAgent. Each entry is a function (modelName) => Model indexed by lowercased provider key. Caller entries merge on top of the defaults, so you can add new keys or replace a built-in. Reach for it on mock providers for tests and fixtures, tenant-specific routing, local-model gateways (Ollama, vLLM via an OpenAI-compatible proxy), auth wrappers, request signing, or regional pinning.

Switching models mid-run is just a different string from a later onTurnPrepared — kernel resolves per turn, so routing logic (cheap model for planning, expensive for synthesis) lives entirely in caller code. 

runAgent({
  state: { runId, context },
  hooks: {
    onTurnPrepared: () => ({
      model: 'openai/gpt-5.5',                  // → openai provider
      messages,
    }),
  },
  modelProviders: {
    mock:   (name) => mockModel(name),       // new provider key
    openai: (name) => signedOpenAI(name),    // override built-in
  },
  // ...
})
Terms

Agent. Caller-owned product behavior around an LLM loop. Kernel does not define a universal agent class.

Run. One durable execution of runAgent with one runId and one AgentRunState.

Turn. One model step: prepare input, call model, record result, execute tools, complete.

Session. Caller concept. Caller decides whether sessions exist and how runs map to them.

Context. Caller-owned JSON carried inside run state and passed through hooks.

Middleware. Caller-supplied wrapper around model or tool I/O for retry, cache, trace, sandbox, fixture, route, or block.
